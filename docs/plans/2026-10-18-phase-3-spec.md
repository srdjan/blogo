### A1 Rederive `validateFrontmatter` (M4, T2)

File: `src/domain/validation.ts`. Today it is one function with
cyclomatic complexity 54.

Contract (from `tests/domain/validation_test.ts` and the code):
- Input `unknown`. A non-object gives `ValidationError`
  `Frontmatter must be an object` with `{ retryable: false }`.
- Every rule adds zero or more messages. All messages are collected and
  joined with `", "` after `Frontmatter validation failed: `. The order of
  messages must stay exactly as today: title, date, slug, excerpt, tags,
  topics, modified, draft, author, category. Inside tags and topics: count,
  then per item, then duplicates.
- Every message text stays byte-identical (copy them from the current file).
- A YAML `Date` value for `date` is normalized to `YYYY-MM-DD`. The output
  `date` is always a string.
- The future-date check skips drafts.

New shape:
- Signature `validateFrontmatter(data: unknown, now: Date = new Date())`.
  The future-date check uses `now`. `content.ts` keeps calling it with one
  argument. Add one test that passes a fixed `now`.
- Pure rule functions that each return `readonly string[]`, for example
  `titleRule`, `dateRule(now)`, an `optionalString(field, label, max?,
  pattern?)` helper for slug, excerpt, author, category, modified, and one
  `stringList(field, singular, plural)` helper shared by tags and topics.
  Read the exact messages before you design the helpers' parameters.
- `validateFrontmatter` runs the rules in order with `flatMap`.
- One `normalizeDate(value: unknown)` used by both the date rule and the
  output normalization.

Target: `validation.ts` max cyclomatic complexity 15 or lower; branch count
lower than today (75). Report both from `deno task metrics` (the per-file
table prints `maxCC`).

Commit: `refactor(validation): rederive frontmatter validation as rule list`.

### B8 `compress` respects `minSize` without `Content-Length`

`src/http/middleware.ts` `compress`. When the response has no
`Content-Length`, read the body into bytes and use its length for the
`minSize` check. Under `minSize`: return a new response with the same
status, headers, and those bytes, not compressed. At or over `minSize`:
compress those bytes. Do this only after the content-type and
`Accept-Encoding` checks, so non-compressible responses (audio, images) are
never read into memory. HEAD handling stays as it is.

Tests: the B8 pin becomes "a small body without Content-Length is not
compressed"; add "a large body without Content-Length is compressed and
decodes to the original".

Commit: `fix(http): apply compress minSize when Content-Length is absent`.
